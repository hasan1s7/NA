# Nabu 1.4.1 — implementation handoff (2026-11-05)

## Source and state

This release was built from the latest **accessible** attached archive, `nabu-connected-learning.zip`, whose root is `nabu-mvp/`. The requested `nabu-next-release.zip` and prior `HANDOFF.md` were not available in the mounted attachments or indexed file search. We therefore worked from 1.4's existing source and its `TEST_REPORT.md`, `START_HERE.md` and code. This HANDOFF is newly authored, not a recovered earlier handoff. All 1.4 features were preserved.

**This is an app/backend source archive, not a hosted site.** Do not copy only `index.html` to GitHub Pages for accounts. Database data, environment files and secrets are deliberately excluded. Do not drop or replace an existing SQLite file.

## Changes in this continuation, relative to 1.4

1. **Tab-safe sync**: use `navigator.locks.request('nabu-sync:'+accountId)` to serialize per-account cloud flushes across tabs where Web Locks is supported, retaining SQLite receipt idempotency everywhere. Recheck the outbox at the end of flushing and schedule work saved during the last network acknowledgment.
2. **Truthful cache status**: after reopening a warm account cache, report `cached`/checking until a server confirmation, rather than `synced`. Network failures remain local/pending, and conflicts continue to require explicit resolution. No pending data is silently discarded.
3. **Backup attestations**: encrypted S3 object uploads include a ciphertext SHA-256 in metadata; HEAD checks verify the metadata and object length before marking the upload confirmed. The local `status.json` records `remoteKey` and `cipherSHA256` after successful upload.
4. **Restore drill command**: `python tools/verify_offsite_backup.py --directory /var/data/backups` downloads and cryptographically checks the last uploaded snapshot, decrypts it, validates SQLite and foreign keys, checks restored sessions are gone, then deletes the isolated temporary copy. Its operator-only success receipt is `restore-drill.json`.
5. **Monitoring**: `tools/backup_status.py --require-offsite --require-restore-drill` fails unless snapshots and a restore drill are recent. The default maximum restore-drill age is seven days; use `--max-restore-age-hours` to tighten it. Health is determined from operator-local receipts, not a public API.
6. **Regression coverage**: added JS cross-tab, in-flight append, and warm-cache tests; added simulated encrypted offsite download/restore, tamper, wrong-key, and monitor tests. Rebuilt the self-contained HTML and changed the service-worker cache/build ID to avoid mixing releases.
7. **Compatibility**: server database schema remains **v3**, API is compatible, SRS remains `nabu-srs-v1`, and guest IndexedDB name/version remains unchanged. Server and `package.json` versions move from 1.4.0 to **1.4.1**.

## Existing 1.4 features retained, not newly claimed

One-use password recovery and session invalidation; private account libraries; offline UUID receipt queue; Learning/Reference/Archived and five-minute skill-specific reviews; natural/literal/usage/example/provenance phrase cards; pasted-text contextual reading; friend requests and direct words; moderated collaborative collections with separate private notes and review schedules; optional private encrypted S3 backup; experimental FSRS read-only analysis script. The phrasebank is a draft and the app is not a certified language resource.

## What to do on a controlled staging host

1. Export the existing guest library JSON and take an *online SQLite backup* of any deployed server before rollout. Keep the previous server/DB. Deploy the **whole** `nabu-mvp/` app on a single backend with an HTTPS origin and persistent private volume. Review Render's charges before choosing any plan. Run `python -m pytest -q` and `node --test tests/*.test.mjs` if you have the development dependencies.
2. Configure private environment variables `NABU_DB`, `NABU_ORIGIN`, `NABU_BACKUP_ENABLED=true`, `NABU_BACKUP_BUCKET`, `NABU_BACKUP_KEY` and private S3 credentials on the host. Keep `NABU_BACKUP_KEY` safe outside the server, or encrypted backups are unrecoverable. A local snapshot alone is not offsite recovery.
3. Make a successful backup, then run `python tools/verify_offsite_backup.py --directory /var/data/backups` on a trusted operator environment able to download the object. Test `python tools/backup_status.py --directory /var/data/backups --require-offsite --require-restore-drill`. Arrange weekly restore drills, alerting and a separate S3 retention/lifecycle policy. Do not use the live DB as the restore target.
4. In at least two real browsers, verify account recovery and session invalidation; sign-in/out isolation; native IndexedDB persistence; disconnected account edits and review, offline reload after service-worker installation, reconnection, Web Locks across tabs and revision conflicts; share roles, proposals, approval, revocation, and non-disclosure of private progress.
5. Perform a provider-cost, security/privacy and language-review pass before a public beta. Do not enable open signups on an exposed staging instance unnecessarily.

## Known remaining work

- **Native HTTPS/browser validation:** blocked here; staging required before release.
- **Offsite disaster recovery:** the downloadable restore drill was tested with a fake S3 client; run it against an actual private bucket and verify it on an isolated host. Monitor snapshot size, retention, alerting and the current 64 MB in-memory encryption limit.
- **Cross-tab fallback:** Web Locks is not universal; per-tab server UUID receipts prevent duplicate commits but non-supporting browsers can still send duplicate HTTP requests. Add a multi-browser compatibility study and test browser shutdown/restarts.
- **Recovery:** codes are strong one-use codes, not email-based reset; users who lose both the password and code cannot self-recover. Don't pretend this is solved.
- **Phrase quality:** 42 phrase/expression draft entries are not independently reviewed; add native review, locale/register, regional usage and targeted learner testing. Natural/literal renderings outside built-in sources may require configured translation providers.
- **Reviews:** per-skill SM-2-inspired scheduling is *not* FSRS; optional read-only replay needs the real `fsrs` package and longitudinal consented review data before considering changes.
- **Scale and privacy:** SQLite single-instance assumptions, receipt history retention, offsite restore rehearsals, backup data deletion, cloud access controls, accessibility, and secure external review remain pre-public-beta tasks.

**Deployment claim:** not deployed; do not treat this archive as live hosting or an operational database.
